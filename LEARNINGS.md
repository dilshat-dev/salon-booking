# Salon Booking --- краткий конспект

## 1. Docker и PostgreSQL

-   **Image** --- шаблон, из которого создаётся контейнер.
-   **Container** --- запущенный экземпляр образа.
-   **Docker Compose** --- описывает сервисы проекта в
    `docker-compose.yml` и запускает их.
-   **Volume** --- постоянное хранилище данных, отдельное от жизненного
    цикла контейнера.
-   **Healthcheck** --- проверяет готовность сервиса. `running`
    означает, что контейнер запущен; `healthy` --- что проверка
    готовности прошла.

В `docker-compose.yml` настроили: - `postgres:17` --- образ PostgreSQL
17 из Docker Hub; - `environment` --- имя БД, пользователя и пароль из
переменных; - `ports` --- проброс порта компьютера `5432` в порт
контейнера `5432`; - `postgres_data:/var/lib/postgresql/data` ---
постоянное хранение файлов PostgreSQL; - `pg_isready` --- проверка
готовности базы.

### Файлы окружения

-   `.env` --- реальные локальные значения; не коммитим.
-   `.env.example` --- шаблон переменных без настоящих секретов;
    коммитим.
-   `.gitignore` содержит `.env`.

Docker Compose автоматически использует `.env` для подстановки
переменных в Compose-файл. Spring Boot при обычном запуске сам по себе
`.env` не загружает.

### Команды Docker / PostgreSQL

``` bash
docker compose up -d
docker compose ps
docker exec -it salon-postgres psql -U salon_user -d salon_booking
```

Внутри `psql`:

``` sql
SELECT version();
\dt
\d salon
\q
```

`Up ... (healthy)` означает, что контейнер работает и проверка
готовности прошла.

## 2. Конфигурация Spring Boot

`application.yml` --- общие настройки:

``` yaml
spring:
  application:
    name: salon-booking
  jpa:
    hibernate:
      ddl-auto: validate
    open-in-view: false
```

`application-local.yml` --- настройки локального профиля:

``` yaml
spring:
  config:
    activate:
      on-profile: local
  datasource:
    url: ${DB_URL}
    username: ${DB_USERNAME}
    password: ${DB_PASSWORD}
    driver-class-name: org.postgresql.Driver
```

**YAML:** вложенность задаётся отступами; используем пробелы, обычно по
два на уровень.

**Spring Profile:** позволяет иметь разные настройки для `local`, `dev`,
`prod`. Общие настройки берутся из `application.yml`, профиль добавляет
или переопределяет свойства.

Запуск с профилем `local`:

``` bash
set -a
source .env
set +a
./mvnw spring-boot:run -Dspring-boot.run.profiles=local
```

`source .env` загружает переменные в текущий терминал; `set -a`
экспортирует их для запускаемых из него процессов.

## 3. JPA и Hibernate

-   **JPA** --- спецификация Java для сопоставления Java-объектов с
    таблицами БД (ORM).
-   **Hibernate** --- реализация JPA.
-   `ddl-auto: validate` --- Hibernate проверяет соответствие Entity
    структуре таблиц, но не создаёт и не изменяет таблицы.
-   `open-in-view: false` --- отключает Open Session in View; доступ к
    данным следует контролировать в сервисном/транзакционном слое.

В нашем проекте Flyway управляет схемой, Hibernate её проверяет.

## 4. Flyway и первая миграция

Flyway --- инструмент версионирования схемы БД. Миграции находятся в:

``` text
src/main/resources/db/migration/
```

Имя `V1__init.sql`: - `V` --- versioned migration; - `1` --- версия; -
`__` --- разделитель; - `init` --- описание.

Создали `V1__init.sql`:

``` sql
CREATE TABLE salon (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(150) NOT NULL,
    time_zone VARCHAR(64) NOT NULL,
    created_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP
);
```

Почему такие типы: - `BIGINT ... IDENTITY` --- большой автоматически
генерируемый идентификатор; - `PRIMARY KEY` --- уникальный и не `NULL`
ключ строки; - `VARCHAR(150)` --- название салона; - `VARCHAR(64)` ---
часовой пояс, например `Asia/Almaty`; - `TIMESTAMPTZ` --- конкретный
момент времени; - `DEFAULT CURRENT_TIMESTAMP` --- БД подставляет время
автоматически, если значение не передано.

Часовой пояс салона хранится отдельно от часового пояса сервера: они
могут находиться в разных регионах.

Flyway ведёт историю в `flyway_schema_history`, применяет новые миграции
по порядку и хранит checksum. Уже применённые миграции не редактируем
--- для изменений создаём новую `V2__...sql`.

Подключили две зависимости: - `spring-boot-starter-flyway` ---
интеграция Flyway со Spring Boot; -
`org.flywaydb:flyway-database-postgresql` --- поддержка PostgreSQL.

## 5. Как проверили работу

В `flyway_schema_history` получили `version = 1`, `description = init`,
`success = t` --- миграция V1 успешно выполнена.

Команда `\d salon` показала четыре ожидаемые колонки и первичный ключ.
Hibernate вывел JDBC URL и версию PostgreSQL 17.11 --- приложение
подключилось к нужной базе.

## 6. Ошибка с паролем

Ошибка `SCRAM ... password is not specified` возникла потому, что
`DB_PASSWORD` был пустым в `.env`.

Важно: изменение `.env` не меняет пароль уже инициализированного
пользователя PostgreSQL в существующем volume. Пароль существующего
пользователя меняют в самой БД, например через
`ALTER USER ... WITH PASSWORD ...`.

### Общая схема ответственности

-   Docker Compose запускает PostgreSQL.
-   `.env` передаёт локальные параметры.
-   Flyway создаёт и изменяет схему БД.
-   JPA/Hibernate сопоставляет Java-классы с таблицами и проверяет
    схему.
-   PostgreSQL хранит данные.
